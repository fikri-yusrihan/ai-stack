# 1. Intake

## Purpose

Turn an ask into an agreed problem statement before anyone researches or designs.

## Why

- Define the problem clearly, because rework often starts with a design that answers the wrong question.
- Write the problem as a cause and its effect, because a symptom alone invites a fix for the symptom, not the cause.
- Get the project owner's agreement on the problem first, because every later step is judged against it.
- Create the folder and README row now, so the work is visible and any session can resume it.

## When to use

Every new ask that is more than a one-file fix or a quick question: a feature, an adjustment, a cleanup, an incident follow-up.

## Owner

- The `general` persona classifies the ask (small and clear, new project, doc phase, plan execution, ambiguous) and writes the problem statement.
- The project owner agrees with the problem statement.

## Inputs and outputs

- In: the project owner's ask in their words; any ticket or chat link.
- Out: a project folder `projects/YYYY-NNN-<name>/` containing `01-research.md` with its header and Problem Statement filled in; a README row. For small work, a direct answer.

## Skill and template

- `start-project` (numbering, folder, header, Phase 0).
- `resume-project` when the ask continues an existing project.
- Template `templates/01-research.md`.

## What to ask

- "Start a project for: <goal>. Target repo: <repo>."
- "Resume projects/YYYY-NNN-<name>."

## Done when

- The project owner agrees with the problem statement, written as a cause and its effect.
- The target repo and service are named.
- The README row exists.
